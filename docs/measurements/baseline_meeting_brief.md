# NFR-002 벤치마크 정확도 베이스라인 — 회의 사전 자료 (#96)

> 작성: 2026-06-13 (회의 전일). 측정 하니스·채점 로직 검증 완료, **14건 전량 측정은 전량 인덱싱 완료 후 본 문서 §5에 기입 예정**.
> 본 자료의 목적은 회의에서 **"NFR-002 정확도 90%의 운영 정의"와 채점 방법론을 숫자 근거로 확정**하는 것이다.
>
> **[2026-06-13 결정] NFR-002 1순위 = 정확한 조항 검색.** 회계사의 전문가적 지식을 신뢰하므로 LLM 답변은 참고용으로 제공한다. 따라서 정확도 헤드라인 = **조항 Hit(특히 "가장 적절한 조항이 최상단" = Hit@1/MRR)**, 답변 내용 correctness는 비헤드라인(Gate B 보조). 측정 하니스·집계도 이 우선순위로 정렬했다.

---

## 1. 배경 / 현황

- 기획서 **NFR-002 = 테스트셋 기준 정확도 90% 이상**. 벤치마크는 34건(K-GAAP 14 + K-IFRS 20)으로 정의되어 있으나 **MVP 측정 대상은 K-GAAP 14건**(`tests/fixtures/benchmark.jsonl`)이다. K-IFRS 20건은 픽스처·인덱스 모두 미존재 → 차기.
- **실측이 한 번도 수행되지 않은 원인 = 인덱싱 미완**. 확인 결과 6/13 작업 전까지 pgvector에는 제21장(20청크)만 적재되어 있었다. 6/13 야간에 `data/ontology/gaap-ch*.json`(전 33장) 전량 적재를 별도 세션에서 진행 중.
- 적재 데이터는 **K-GAAP 전용**이므로, 벤치마크 `references`의 두 항목(`일반기업회계기준 …` / `K-IFRS 제…호 …`) 중 **K-GAAP 조항만 채점 대상**으로 삼는다.

## 2. 현행 채점 코드 진단 (구조적 결함)

`tests/integration/test_benchmark_compliance.py`의 세 테스트 중 핵심인 `test_reference_coverage`:

```python
all_citation_text = " ".join(c.content for c in response.citations)
matched = [ref for ref in case.references if ref in all_citation_text]
assert len(matched) > 0
```

- **결함**: 정답 라벨은 `"일반기업회계기준 제18장 18.7조"` 형태인데, 청크 본문에는 `#### 18.7` 형태로 **문단번호만** 존재한다. 라벨 문자열 전체가 본문에 없으므로 부분일치는 **거의 항상 실패**한다.
- **실증**: §4의 라이브 스모크에서 `legacy_substring = False` (정답 조항이 실제 인용됐어도 라벨 매칭은 실패).
- 또한 **번호 오류 / 내용 상이 / 무관**의 실패 모드를 분리하지 못한다.

## 3. 채점 방법론 — 측정 하니스 (회의 결정 안건)

채점 방법론이 미결정이므로, **단일 점수로 합치지 않고 여러 지표를 동시에 산출**하는 측정 하니스를 구현했다 (`scripts/benchmark_baseline.py`). 회의에서 이 숫자들을 비교해 NFR-002의 운영 정의를 확정한다.

| 지표 | 정의 | 용도 |
|---|---|---|
| `legacy_substring` | 현행 방식(라벨 문자열 부분일치) 재현 | 결함 대조군 |
| `clause_exact` | 정규화 조항키(문단번호) 정확 교집합 | **NFR-002 후보 (엄격)** |
| `clause_prefix` | 계층 매칭 (gold `2.6.5` ↔ 청크 `2.6` 허용) | 입도 불일치 보정 |
| `is_answerable` | 답변 가능 플래그 일치 | 가드레일 |

- 각 조항키 지표는 **검색단계(`reranked_chunks`)와 생성단계(`citations`) 양쪽에서** 측정 → "검색이 못 찾음" vs "찾았는데 인용 누락"을 분리.
- Hit@1 / Hit@k(k=10=`TOP_K_RETRIEVAL`) / MRR / Recall 동시 기록.
- 권장 2-티어 구조(2026-06-07 D1 B안과 정합):
  - **Gate A (1순위, NFR-002 = 이 숫자)** — 조항 검색 정확도 (`clause_*` Hit@k)
  - **Gate B (2순위, 보조)** — 답변 품질 (LLM-as-judge, Gate A 통과분 한정)

> 참고: 현재 UI(`app.py`)는 회계사에게 **답변이 인용한 조항(`citations`)만** 노출한다. "조항 1순위" 철학과 달리 조항 제공이 답변 인용에 종속되어, 검색이 정답을 올려도 답변이 인용하지 않으면 회계사가 볼 수 없다 → §6 개선후보(검색된 조항 우선 제시).

## 6. 개선 후보 (우선순위)

검색 Hit = 생성 Hit → **검색 정밀도가 병목**. 실패 모드 기반 우선순위:

1. **🔝 리랭킹 활성화 (`USE_RERANKER=false`→`true`)** — Hit@10=42.9%인데 **Hit@1=21.4%**(MRR 0.21), 정답이 검색돼도 최상단이 아닌 경우 다수(모드A). 게다가 008은 데이터 양에 따라 hit↔miss **진동**(§5) — 1차 검색 점수만으로 정렬돼 경계선 케이스가 불안정. Cross-encoder 재정렬로 정답 문단 상위 고정 → "가장 적절한 조항 최상단"(1순위) 직접 효과 + 안정화. **저비용·고효과 1순위.**
2. **장(chapter) 라우팅/필터** — 모드B(006·011): 주제어 유사성으로 엉뚱한 장 검색. 질의→장 분류 또는 metadata 필터로 후보 장 제한.
3. **청크 입도 / `paragraphs` 메타데이터** — 모드A: 정답 옆 문단만 인용. 청크 metadata에 문단번호 부여(검색·채점 동시 개선) + 인접 문단 병합 검토.
4. **벤치마크 gold 라벨 검증** — 모드C(001 2.6.5): 정답 라벨이 실제 문단 체계와 불일치. 14건 gold 재확인(채점 분모 신뢰성).
5. **CRAG needs_external** — 전량 적재 후 대부분 CRAG=1로 완화(008: 3→1). 011만 CRAG=2. 우선순위 하향, 단 `evaluate.py:209` 키워드 오버라이드 잔존 위험.
6. **`legacy` 문자열 채점 폐기 → `clause_exact` 정식 전환** — 0% 확정.

## 7. 회의 결정 필요 항목 (Open Questions)

1. **NFR-002 운영 정의** — 1순위 = 조항 Hit으로 **확정(6/13)**. 남은 세부: 지표(`clause_exact` vs `clause_prefix`), 합격선·k(Hit@1 vs Hit@k). 권고: 회계사 제공물 기준 = **생성단계 `clause_exact`**, "가장 적절한 조항 최상단" = **Hit@1/MRR 중시**. 잠정 합격선: *생성 `clause_exact@10` ≥ 90% (Hit@1 보조 추적)*.
2. **조항 입도 정책**: 문단(`2.6`) 기준 vs 세부 호(`2.6.5`) 기준 — `clause_prefix` 채택 여부.
3. **청크 metadata에 문단번호(`paragraphs`) 부여** — 채점·검색 정밀화 선행 작업.
4. **LLM-as-judge 도입 범위**(Gate B) — 모델/프롬프트/비용.
5. **CRAG needs_external 오탐 fast-follow** 우선순위.
