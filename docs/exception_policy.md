# MVP 예외 처리 정책

> AccountingRAG 시스템의 예외 처리 일관성 기준
>
> 작성일: 2026-06-13
> 상태: 제안 (정책 메타이슈 합의 후 확정)

---

## 1. 배경 — 왜 정책이 필요한가

현재 코드베이스의 문제는 예외 처리가 **너무 많아서**도, **너무 적어서**도 아니라 **일관성이 없어서**다.

- 한쪽에는 에러코드(CM/PS/OT/SE/RR/IX/EV/GN-xxx) + `is_retryable` 플래그 + `to_error_log()`까지 갖춘 **정교한 분류 체계**(`src/utils/exception.py`)가 있다.
- 그런데 `is_retryable=True`는 어떤 재시도 루프로도 이어지지 않고(읽는 코드 0건), 정의만 되고 한 번도 `raise`되지 않는 예외 클래스가 다수 존재한다.
- 반대쪽에는 그 체계를 무시하고 실패를 조용히 삼키는 지점이 공존한다.

즉 **비싼 분류 인프라를 깔아놓고 절반만 배선한 상태**다. 이 정책은 "어떤 예외든 처리 방식을 셋 중 하나로 강제"해 그 불일치를 제거한다.

---

## 2. 핵심 원칙 — 모든 예외는 3종 처분 중 하나를 가진다

| 처분 | 의미 | 코드 형태 | 대표 대상 |
|------|------|-----------|-----------|
| **RETRY** | 일시 장애 → 정해진 횟수만 재시도 | **실제 재시도 루프/재진입 엣지에 반드시 연결**. 연결할 수 없으면 RETRY 자격을 박탈하고 DEGRADE/FAIL-FAST로 재분류한다. | LLM API 일시 연결 실패, pgvector 타임아웃, 검색 결과없음 후 CRAG 재진입 |
| **DEGRADE** | 실패해도 흐름은 계속, 단 **로그 + `error_logs` 누적 필수** | silent 금지. 항상 `error_logs`에 적재하고 graceful 기본값을 반환한다. | rewrite 전략 실패, 리랭크 임계 미달, 임베딩 토큰 한도 초과 스킵 |
| **FAIL-FAST** | 즉시 중단, 구조화된 에러를 호출부까지 전파 | 정상 흐름으로 복구 불가. 구조화 반환 계약(노드 → 상태)을 깨지 않고 전파한다. | 설정 누락, 지원 안 되는 포맷, 컨텍스트 길이 초과, 빈 질의 |

> **3종 외 처리는 금지한다.** "잡았지만 아무것도 안 함", "정보 추가 없이 다시 감싸 던짐", "절대 트리거되지 않는 방어"는 모두 정책 위반이다.

## 3. 도출 규칙 (정렬 작업의 판단 기준)

이 정책에서 다음 규칙이 자동으로 나온다. 정렬 이슈들은 모두 이 규칙 위반을 고치는 작업이다.

### R1. RETRY는 실제 재시도에 연결되어야 한다
`is_retryable=True`인데 재시도 루프가 없으면 둘 중 하나로 정정한다 — (a) 실제 재시도 루프/재진입에 연결하거나, (b) DEGRADE/FAIL-FAST로 재분류. **플래그만 있고 배선 안 된 상태**가 현재 "이도저도"의 핵심이다.

### R2. 처분이 없는 분류는 제거한다
한 번도 `raise`되지 않는 예외 클래스, 던지지 않고 로그 포맷 용도로만 생성하는 예외 객체는 유지 비용만 발생시킨다 → 삭제하거나 실제 `raise` 사이트와 함께 도입한다(YAGNI).

### R3. DEGRADE 지점에서 silent 삼킴은 금지
실패를 삼키고 기본값만 반환하면서 `error_logs`에 남기지 않으면 관측 불가능한 버그가 된다. 기존 #129·#130이 정확히 이 규칙 위반 사례이며, 본 정책은 그 이슈들과 **상호보완**이다.

### R4. 도달 불가능한 방어는 제거한다
프로덕션 경로에서 절대 트리거될 수 없는 except(예: 호출 라이브러리가 그 예외를 던지지 않음, 이미 보장된 불변식 재검증)는 거짓 안전감만 준다 → 제거하거나, 실제로 트리거되도록 변환 계층을 배선한다.

### R5. 호출부 처분이 같은 세분 예외는 병합을 검토한다
서로 다른 에러코드라도 호출부에서 동일하게 처분(예: 전부 같은 DEGRADE 폴백)된다면 분리 유지의 가치가 낮다 → 병합 검토. 단 의미가 실제로 다르고 향후 분기 가능성이 있으면 유지.

## 4. 기존 강화 이슈와의 관계

다음 열린 이슈들은 "누락(under-handling)" 측 정렬 작업으로, 본 정책 아래 자연스럽게 포섭된다. 충돌이 아니라 같은 정책의 반대편 절반이다.

- **#129** search가 임베딩 일시장애(CM-002)를 결과없음(SE-103)으로 오처리 → R1/R3 (RETRY 대상을 DEGRADE로 잘못 처분)
- **#130** rewrite 노드 LLM 실패가 silent → R3 (DEGRADE인데 `error_logs` 누락)
- **#131** run/resume_workflow의 TimeoutError 미처리 재전파 → FAIL-FAST 구조화 계약 위반
- **#134** index_documents 부분실패 시 손실 청크 복구 신호 부재 → R3 (DEGRADE 관측성)
- **#135** 리랭커 import-time 모델 로드 실패 graceful fallback → DEGRADE 정합화

---

## 5. 적용 범위 / 비범위

- **범위**: `src/` 전역의 커스텀 예외(`AccountingRAGError` 계열)와 그 처리 코드.
- **비범위(MVP 단계)**: tenacity 등 본격 재시도 프레임워크 도입, 분산 트레이싱, 예외 → 사용자 메시지 i18n. 이들은 v1.1 이후 검토.

> 향후 진짜 재시도 루프를 도입하기 전까지 **`is_retryable` 같은 불리언 신호에 의존하는 새 분기를 추가하지 말 것**. 재시도 여부는 예외 *타입*으로 판단한다.
